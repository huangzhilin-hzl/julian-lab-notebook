Hy3 正式版模型发布摘要

基于 Tencent 在 Hugging Face 发布的 tencent/Hy3 模型卡、raw README、config、finetune README 和 Hy3-FP8 仓库元数据整理；采集时间为 2026-07-06。

License Apache-2.0
Sibling Model Hy3-FP8
295B MoE 21B active 256K context MTP serving tool calling BF16 / FP8
结论：Hy3 是 Hy3 Preview 之后的正式 instruct release，核心变化不是架构规模大改，而是 post-training / RL / 产品反馈闭环加强。模型卡把它定位成面向 coding、agent、长上下文和生产工具调用的 MoE 大模型；真正落地时重点看 vLLM/SGLang 的 Hy3 parser、MTP speculative 路径和 8 卡大显存部署条件。

Model Specs

Item Value Notes
Architecture MoE, model_type=hy_v3, HYV3ForCausalLM 192 experts, top-8 activated; config also exposes one shared expert and sigmoid router with expert bias.
Scale 295B total, 21B active, 3.8B MTP layer parameters HF side metadata reports about 299B params; the model card uses 295B as the canonical total parameter count.
Transformer shape 80 layers, hidden size 4096, intermediate size 13312 GQA with 64 attention heads, 8 KV heads, head dimension 128.
Context 256K tokens config.json uses max_position_embeddings=262144.
Vocabulary 120832 Tokenizer/template uses Hy-specific role, think, tool-call and tool-response special tokens.
Precision BF16 main release; FP8 sibling release Hy3-FP8 exposes quantization_config.quant_method=fp8.
Generation defaults temperature=0.9, top_p=1.0 Reasoning mode is controlled by reasoning_effort: no_think, low, or high.

Positioning

Area Claim Reported evidence Engineering read
Preview -> Hy3 正式版吸收 50+ 产品团队反馈，修复任务执行和交互问题，并扩大 post-training pipeline。 模型卡强调 RL 规模、post-training 数据质量和多样性提升。 这说明 Hy3 正式版更像产品化 alignment release，而不是只发布新的 base architecture。
Agent / productivity 在 coding、文档处理、金融分析、游戏开发、前端设计等生产力场景有明显增强。 270 位专家盲测、312 个有效比较中，Hy3 为 2.67/4，GLM-5.1 为 2.51/4；优势集中在前端、CI/CD、数据与存储。 官方更重视真实 workflow 体验；公开 benchmark 仍需要和内部盲测分开看。
Tool calling 输出格式、工具调用成功率、错误恢复和跨 scaffold 泛化改善。 SWE-Bench Verified 上 CodeBuddy、Cline、KiloCode 等 scaffold 的准确率波动在 4% 以内。 部署时需要使用 Hy3 专用 parser：vLLM 的 hy_v3 或 SGLang 的 hunyuan。
Anti-hallucination 更强调有依据时回答、缺证据时说明、不混淆来源、不编造数据。 内部评测中 hallucination 从 12.5% 降到 5.4%，commonsense error 从 25.4% 降到 12.7%。 对企业工具链是好信号，但指标来自内部评测，外部复现需要独立评测集。
Long context / multi-turn 提升指代消解、省略恢复和多轮约束继承。 内部多轮综合测试问题率从 17.4% 降到 7.9%；MRCR 从 42.9% 提升到 75.1%。 256K context 只是容量前提，真实效果还取决于 serving KV 管理、prompt 组织和长上下文 eval。

Serving

Stack Official recipe Key switches Notes
vLLM Build from source, serve tencent/Hy3 with TP=8 and OpenAI-compatible API. --speculative-config.method mtp, --speculative-config.num_speculative_tokens 2, --tool-call-parser hy_v3, --reasoning-parser hy_v3, --enable-auto-tool-choice. README additionally sets VLLM_FLASHINFER_ALLREDUCE_BACKEND=trtllm as a workaround for an MNNVL workspace-size issue.
SGLang Build from source, install transformers>=5.6.0, launch python3 -m sglang.launch_server. --tp-size 8, --tool-call-parser hunyuan, --reasoning-parser hunyuan, --speculative-num-steps 2, --speculative-eagle-topk 1, --speculative-num-draft-tokens 3, --speculative-algorithm EAGLE. 这里的 EAGLE 参数是在承载 MTP draft/verify 形态；需要用支持 Hy3 parser 和 speculative 路径的较新 SGLang。
Hardware 官方建议 8 GPUs，使用 H20-3e 或其他更大显存 GPU。 BF16 权重按 295B 参数粗略估算约 590GB 权重体积，不含 KV cache、workspace 和 runtime overhead。 256K context 下 KV cache 压力会成为部署上限之一；FP8 版本可减轻权重显存，但仍需验证精度、吞吐和框架兼容。
Client API OpenAI-compatible /v1/chat/completions after starting vLLM/SGLang. extra_body={"chat_template_kwargs": {"reasoning_effort": "no_think"}} for direct response; use high for complex math/coding/reasoning. HF model page currently says it is not deployed by an Inference Provider, so users should assume self-hosted serving unless that status changes.

Finetuning And Quantization

Track Official content Operational implication
Training format 训练数据按 message list 组织；支持 fast thinking 和 slow thinking，依赖 reasoning_effort 与 reasoning_content。 SFT 数据需要显式区分是否保留 reasoning；这会影响 chat template 与输出风格。
Checkpoint conversion 原始 checkpoint 中每个 expert 独立存储；官方建议转换成 HF-compatible outer format，把多 expert 权重融合为统一 3D tensor key。 大规模训练前应先跑 conversion 和 validation；否则加载速度和跨 shard expert group 处理会成为成本。
Training methods 提供 DeepSpeed native、LLaMA-Factory、ms-swift 三条路径。 这比只给推理权重更完整，但生产微调仍要重点验证 optimizer/offload、sequence length 和多机 SSH/共享盘约束。
Hardware 在 max_seq_length=4096 且特定配置下，LoRA 至少单机 8x80GB；full fine-tuning 至少 4 机 32x80GB。 这不是轻量微调模型；LoRA 都需要完整 8 卡 80GB 级别机器。
Quantization 官方发布 Hy3-FP8，并推荐 AngelSlim 做大模型压缩，覆盖常见量化、低比特量化和 speculative sampling。 FP8 是优先试的部署形态；W4A8/int4 类路径可参考 AngelSlim，但模型卡没有直接给出 Hy3 正式版完整精度/吞吐表。

Risks And Follow-ups

Question Current answer Follow-up check
正式版相对 Preview 的架构差异有多大？ 模型卡参数表与 Preview 很接近，主要叙事集中在 post-training、RL、工具调用和产品反馈修复。 如果要写更强结论，应 diff Hy3 与 Hy3-preview 的 config.json、template 和 generation config。
vLLM/SGLang 哪个更稳？ 官方同时给 recipe；vLLM recipe 显式给 hy_v3 parser 和 allreduce backend workaround，SGLang recipe 给 hunyuan parser 和 EAGLE speculative 参数。 需要在目标集群上分别跑 8 卡 smoke，重点看 MTP acceptance、tool-call parser、长上下文 KV cache 和 FP8 path。
公开指标是否足够？ 模型卡给了内部产品指标和 blind test，但公开页面没有完整可下载 benchmark 明细。 对研发采用应补 SWE-Bench/Terminal-Bench/长上下文/工具调用自有 eval，避免只看官方 aggregate。
Apache-2.0 是否覆盖所有使用场景？ Hy3 正式版模型卡标记 Apache-2.0；这比 Preview 的许可约束更宽松。 上线前仍应查 LICENSE 原文、依赖 tokenizer/template 代码和下游分发条款。
